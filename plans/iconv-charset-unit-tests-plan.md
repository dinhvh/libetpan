# Unit coverage for every charset listed by iconv

## Goal

Test libetpan's conversion APIs against every charset name in a recorded Linux `iconv --list` inventory, with fixtures grouped into two data files. Use the suite to measure ICU-only coverage and detect regressions when iconv is disabled.

This is a plan only. The existing Linux implementation changes remain uncommitted.

## Inventory and scope

The current machine reports **1,180 names** using Ubuntu glibc iconv 2.43 (`2.43-2ubuntu2.4`). These are names and aliases, not necessarily 1,180 distinct encodings. Preserve the original inventory, provider/version, and capture procedure. Remove glibc's trailing `//` display suffix when constructing test names; do not remove meaningful punctuation or collapse aliases before testing them.

The inventory varies by iconv provider, installed conversion modules, and platform. Commit a fixed Linux inventory so normal unit tests are deterministic. Refresh it deliberately when changing the supported baseline; do not enumerate the host at every test run.

Cover conversion between UTF-8 and each listed charset in both directions, rather than testing every possible charset pair. Exercise both `charconv()` and `charconv_buffer()`. Include names that are aliases and obscure/vendor encodings, recording limitations explicitly.

## Test layout

Extend the existing `unittest/charconv/charconv_test` target rather than creating hundreds of executables:

- `unittest/charconv/charset_cases.h`: shared case schema and group declarations.
- `unittest/charconv/charset_singlebyte_cases.c`: ASCII-compatible single-byte, ISO-8859, Windows, DOS, EBCDIC, and other single-byte cases and aliases.
- `unittest/charconv/charset_multibyte_cases.c`: Unicode, East Asian, stateful, and other multibyte cases and aliases.
- `unittest/charconv/charset_cases_test.c`: shared runner, assertions, coverage accounting, and diagnostics.
- `unittest/charconv/data/iconv-glibc-charsets.txt`: exact normalized name inventory and provenance comments.

Keep the current focused API/error/callback tests in `main.c` and invoke the new grouped suite from there. Share byte vectors where aliases are verified to behave identically, but retain a test entry for every name. A name that cannot yet be classified must remain accounted for rather than being dropped.

Keep any manual fixture-generation or provider-comparison utility in `tests/`, following AGENTS.md's placement of manual diagnostic tools. Generated deterministic fixtures and their runner belong in `unittest/`.

## Fixture design

Each case records:

1. Exact charset name and family/group.
2. Source bytes, source length, expected UTF-8 bytes, and expected length for decoding.
3. UTF-8 input and expected target bytes for encoding, where supported.
4. Explicit expectations for iconv-only, ICU-only, and the current dual-backend configuration.
5. Notes for aliases, mapping differences, directional restrictions, or platform dependence.

Use explicit byte arrays and lengths, not source-file encoding or `strlen()` as the binary-data oracle. Include embedded NULs and terminator checks separately. For `charconv()`, compare the known expected byte span and final NUL; use `charconv_buffer()` to verify the returned binary length.

For each distinct mapping, choose at least one non-ASCII representable character when the encoding supports one. ASCII-only probes cannot distinguish most legacy encodings. Add boundary and distinctive mapping characters to families where one character would leave important differences untested. EBCDIC needs encoded ASCII text as well as distinctive characters; Unicode needs supplementary characters and byte-order/BOM cases; stateful encodings need shift transitions and end-of-input handling.

Do not assume every encoding can represent the same sample string. Select suitable per-family samples and record a reason where an encoding supports only decoding, only encoding, or cannot be exercised portably.

## Build the reference data

1. Capture the complete list and provider/version using a manual utility such as `tests/generate-charconv-charset-fixtures.py`.
2. Convert selected Unicode samples using the reference iconv provider, checking exit status, complete input consumption, and exact output bytes. Run subprocesses with timeouts, explicit arguments, and binary input/output. Avoid `//IGNORE`, `//TRANSLIT`, and `-c` when generating valid-input fixtures.
3. Decode generated bytes back to UTF-8 to confirm the intended characters. Do not assume a round trip is bijective: duplicate mappings and canonicalization need explicit reference vectors for each direction.
4. Review and save literal byte fixtures. Expected output must not be generated using libetpan itself or the backend under test during a normal unit run.
5. Verify aliases through actual reference conversions before sharing vectors. Similar spelling does not prove identical behavior.
6. Classify names that depend on host byte order, native representation, conversion modules, or unavailable direction support. Add architecture-specific expectations where meaningful; otherwise provide a precise, visible limitation with an associated test where possible.

Respect libetpan's intentional normalization, such as GB2312 to GBK and ISO-2022-JP to ISO-2022-JP-2. Use samples in the common repertoire for basic comparisons and dedicated cases for normalization behavior. Reference expectations for these dedicated cases must come from the effective normalized encoding, with that difference recorded.

## ICU comparison and acceptance policy

Do not assume ICU recognizes every name or implements the same mapping as glibc iconv. First produce a report separating:

- Names with identical tested output.
- Names needing a verified alias normalization.
- Names recognized by both backends with different character mappings or stateful output.
- Names unsupported by ICU, or requiring converter data absent from the packaged ICU build.
- Names whose reference iconv conversion cannot be exercised portably.

Use explicit backend expectations reviewed from this report. An ICU unsupported-name case should assert `MAIL_CHARCONV_ERROR_UNKNOWN_CHARSET`; it must appear in the coverage summary as unsupported, not as a successful conversion or a silent skip. Baseline-supported cases must fail on later loss of support or changed output. Newly supported names should trigger review of their expected vectors.

Distinguish ICU-only from dual-backend behavior: the latter currently routes only selected Japanese source encodings through ICU. Selecting expectations solely on `HAVE_ICU` would be incorrect.

Fix proven alias gaps in the implementation separately from fixture creation. Do not automatically normalize arbitrary punctuation or manufacture expected bytes to hide mapping differences. Where ICU has no equivalent converter, preserve a documented coverage gap; if complete iconv compatibility becomes a requirement, that gap prevents declaring ICU-only a full replacement.

Keep malformed-input and unmappable-output tests separate from valid-input equivalence tests. ICU and the existing iconv wrapper have different substitution rules; enforce the deliberately supported behavior for each backend rather than demanding accidental byte-for-byte equivalence. Check that ICU's packaged data is present for the supported baseline.

## Build integration and diagnostics

Update `CHARCONV_TEST_SRCS` and `CHARCONV_TEST_DEPS` in `unittest/Makefile` for the new files and inventory. Add an inventory-completeness check that fails on duplicate entries, missing listed names, or fixture names absent from the inventory. Normal unit execution must not require the iconv command or reference libiconv when testing ICU-only.

Print a compact summary showing total names, successful decode/encode cases, supported ICU names, documented unsupported names, and platform-limited cases. Totals must reconcile with the complete inventory. Failures should identify name, backend, API, direction, expected/actual error or bytes, and first differing offset. Aggregate failures so a large inventory produces one useful report instead of stopping at the first unsupported name.

## Validation and completion criteria

Run the expanded target and full existing suite after clean builds for:

- ICU-only: `--with-icu=yes --disable-iconv`.
- Dual backend: `--with-icu=yes --enable-iconv`.
- iconv-only: `--with-icu=no --enable-iconv`.

Retain the previously identified iconv-only Japanese rendering fixture failure as a separately reported baseline limitation. The new charset target should have independently assessed expectations for that backend.

Verify compiled backend defines and symbol references; rebuild test binaries when switching configurations. Confirm ICU-only tests run without linking iconv directly and without invoking the iconv executable. Run the deterministic fixture suite on another supported Linux architecture/provider configuration to check explicit portability handling.

The work is complete when all 1,180 baseline names are accounted for, every supported direction has reviewed byte fixtures through both APIs, backend differences and unsupported names are visible, completeness checks pass, and the existing ICU-only message fixtures continue to pass. Report conversion coverage separately from inventory accounting so testing an unsupported name is never presented as supporting that encoding.
